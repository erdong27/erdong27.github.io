Deployment 声明式管理与滚动更新

前两篇聊了 K8s 的整体架构和 Pod，今天来聊真正在生产中最常用的资源——Deployment。

如果说 Pod 是 K8s 里的”进程”，那 Deployment 就是 Pod 的”管家”：它帮你管数量、管版本、管更新，让你不用手动盯着每一个 Pod。

一、为什么需要 Deployment？

先想一个问题：如果直接用 Pod，会碰到什么问题？

1.1 裸 Pod 的痛点

假设你直接用 kubectl run 创建了 3 个 Nginx Pod，现在你想把镜像从 nginx:1.24 升级到 nginx:1.25。怎么办？

麻烦不说，升级过程中服务还会中断。如果有 100 个 Pod 呢？手动操作简直是噩梦。

更别提这些场景：

  • Pod 挂了，谁来自动拉起来？
  • 想从 3 个副本扩容到 10 个，怎么操作？
  • 新版本有问题，怎么快速回滚？

裸 Pod 一个都解决不了。这就是 Deployment 存在的意义。

1.2 Deployment 解决了什么

Deployment 是 K8s 里管理无状态应用的标准方式，它帮你解决：

问题 Deployment 的解法
Pod 挂了怎么办？ 自动重建（ReplicaSet 保证副本数）
怎么升级版本？ 滚动更新（逐批次替换，服务不中断）
新版本有问题？ 一键回滚（kubectl rollout undo）
怎么扩缩容？ 改一个数字（kubectl scale）
升级到一半想停？ 暂停/恢复（rollout pause/resume）

二、声明式管理是什么？

K8s 的核心设计理念就是声明式（Declarative），理解这个概念对用好 K8s 至关重要。

2.1 命令式 vs 声明式

命令式：你告诉系统”怎么做”

声明式你在 YAML 文件里描述”期望状态”，K8s 自己想办法达到这个状态：

两者的核心区别：

命令式 声明式
思维方式 一步步操作 描述目标状态
可重复性 差（操作步骤散落各处） 强（YAML 就是完整记录）
版本管理 难以追踪变更 YAML 可直接用 Git 管理
适合场景 临时调试 生产环境、CI/CD

生产环境永远用声明式，把 YAML 文件存进 Git，这就是现在流行的 GitOps 的雏形。

六、扩缩容

6.1 手动扩缩容

底层原理：Deployment 修改 spec.replicas，ReplicaSet 感知到变化后，创建或删除 Pod 来达到目标数量。

6.2 基于 CPU 使用率的自动扩缩容（HPA）

手动扩缩容太麻烦，K8s 提供了 HPA（Horizontal Pod Autoscaler） 根据 CPU/内存使用率自动调整副本数。

（HPA 的详细用法会在 Day 13 深入讲解，这里先了解基本概念。）

七、Deployment 与 ReplicaSet 的关系

很多人会疑惑：为什么我创建了 Deployment，却看到 ReplicaSet 也出现了？

这是 K8s 的设计：Deployment 不直接管理 Pod，而是通过 ReplicaSet 间接管理。

每次更新 Deployment，K8s 会：

  1. 创建一个新的 ReplicaSet（新版本）
  2. 新 ReplicaSet 逐步增加副本
  3. 旧 ReplicaSet 逐步减少副本
  4. 完成后，旧 ReplicaSet 保留（用于回滚），但副本数变为 0

所以 kubectl get rs 看到的 ReplicaSet 数量 = 更新历史数量（受 revisionHistoryLimit 限制）。

总结

Deployment 是 K8s 里最常用的资源，理解它是生产运维的基础：

  • Deployment 管理 ReplicaSet，ReplicaSet 管理 Pod，三层结构各司其职
  • 声明式管理是 K8s 的核心理念，用 YAML 描述期望状态而不是一步步操作
  • 滚动更新让服务升级不中断，maxSurge 和 maxUnavailable 控制更新节奏
  • 一键回滚拯救发布事故，revisionHistoryLimit 控制保留多少历史版本
  • 扩缩容支持手动和自动（HPA）两种方式
