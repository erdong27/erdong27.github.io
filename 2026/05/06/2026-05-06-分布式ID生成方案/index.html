版本说明

⚠️ 本文基于以下版本编写：

  • Java: 8 / 11 / 17
  • Snowflake: Twitter 原始算法
  • Leaf: 美团 Leaf 3.0+

一、为什么需要分布式 ID

在单机系统中，数据库自增 ID 或 UUID 就能满足需求。但在分布式环境下，这些问题就暴露出来了：

传统方案的问题

方案 问题
数据库自增 单点故障、性能瓶颈、分库分表后 ID 冲突
UUID 无序导致 B+ 树索引分裂、太长（36字符）、无业务含义
Redis INCR 依赖 Redis、网络开销、Redis 挂了怎么办

分布式 ID 的要求

一个合格的分布式 ID 生成方案应该满足：

  1. 全局唯一性：不能出现重复 ID
  2. 有序性：趋势递增，利于数据库索引
  3. 高性能：高并发下生成速度快
  4. 高可用：单点故障不影响整体服务
  5. 信息安全性：不能泄露业务量等信息

二、雪花算法（Snowflake）

Twitter 开源的分布式 ID 生成算法，最经典的解决方案。

ID 结构（64位 Long）

  • 1 位符号位：始终为 0
  • 41 位时间戳：毫秒级时间，可用约 69 年
  • 10 位工作机器 ID：最多 1024 个节点
  • 12 位序列号：同一毫秒内最多生成 4096 个 ID

六、方案对比

方案 性能 可用性 依赖 适用场景
Snowflake 极高（400万QPS） 一般（时钟回拨风险） 无 中小规模、对 ID 有序性要求不高

九、总结

分布式 ID 生成是分布式系统的基础设施，选型时需要考虑：

  1. 性能要求：QPS 是否需要百万级？
  2. 有序性要求：是否需要严格递增？
  3. 依赖成本：是否接受引入 ZK/MySQL？
  4. 运维成本：机器 ID 分配、时钟同步等

推荐方案：

  • 小项目 → 雪花算法
  • 大项目 → Leaf-segment
  • 有序性要求高 → Leaf-snowflake
  • 超大规模 → TinyID
