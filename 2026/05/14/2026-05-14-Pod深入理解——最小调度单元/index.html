Pod 深入理解——最小调度单元

上一篇文章我们聊了 K8s 的整体架构，今天把目光聚焦到 Kubernetes 里最基础也最重要的概念——Pod。

如果你把 K8s 想象成一个操作系统，那 Pod 就是这个系统里的进程。你所有的应用最终都会跑在一个个 Pod 里面。理解了 Pod，就理解了 K8s 的一半。

一、为什么需要 Pod？

很多刚接触 K8s 的人都会有一个疑问：Docker 已经有容器了，为什么 K8s 还要搞一个 Pod 出来？直接调度容器不就行了吗？

这个问题的答案藏在真实的生产场景里。

1.1 容器不是万能的

一个容器只做一件事，这是 Docker 的设计哲学。但现实世界中，有些任务天然需要多个进程紧密配合。

举个例子：你有一个 Java Web 应用，它的日志文件需要用一个 Fluentd 容器实时采集并转发到日志中心。这两个容器：

  • 必须部署在同一台机器上（共享日志文件）
  • 必须同时启动、同时销毁
  • 共享同一个网络命名空间（可以直接用 localhost 通信）
  • 共享存储卷（Fluentd 读 Java 写的日志）

如果只调度”容器”，你要自己维护这些容器之间的关联关系，K8s 调度器也没法保证它们一定被分到同一台机器。

1.2 Pod 就是答案

Pod 把一组紧密耦合的容器打包成一个调度单元：

简单说：Pod 是 K8s 能调度的最小单位，一个 Pod 里可以跑一个或多个容器。

二、Pod 的网络模型

Pod 的网络设计非常简洁优雅，理解了它，后面排查网络问题会轻松很多。

2.1 一个 Pod 一个 IP

每个 Pod 启动时会分配一个集群内部 IP，这个 IP 是 Pod 里所有容器共享的。

这意味着什么？同一个 Pod 里的两个容器，可以直接用 localhost:端口 互相通信，就像跑在同一台机器上的两个进程一样。

2.2 Pod 之间怎么通信？

不同 Pod 之间直接用 Pod IP 通信，不需要 NAT（网络地址转换）。这个模型叫做 “每 Pod 每 IP”（One IP Per Pod）。

实际是由节点上的 CNI 插件（如 Flannel、Calico、Cilium）来实现的底层网络互联。你不用关心细节，但要知道 K8s 的网络模型是这样的。

2.3 localhost 的坑

正因为共享网络命名空间，同一个 Pod 里的容器不能使用相同的端口。如果 App 容器占了 8080，Sidecar 就不能用 8080。

这是很多人常犯的错，尤其是从 Docker Compose 迁移过来的人——在 Compose 里每个容器有独立网络，端口不冲突；但在 Pod 里，端口是共享的。

三、Pod 的存储模型

容器本身是临时的，容器被销毁，里面的数据就没了。Pod 里的容器需要持久化数据怎么办？答案是 Volume。

3.1 Pod 内共享 Volume

Volume 定义在 Pod 级别，Pod 里的所有容器都可以挂载同一个 Volume。

这里 emptyDir 是一种简单的临时卷，Pod 销毁后数据也没了。如果需要持久化，可以用 hostPath、NFS 或者后面会讲到的 PV/PVC。

四、Pod 的生命周期

Pod 从创建到销毁会经历一系列状态变化，搞清楚这些状态对排查问题非常重要。

4.1 Pod 的五种状态

状态 含义 常见原因
Pending 已被接受但容器还没启动 镜像拉取中、调度中、资源不足
Running 至少一个容器正在运行 正常运行
Succeeded 所有容器正常退出 一次性任务（Job）执行完成
Failed 至少一个容器异常退出 程序崩溃、OOM 被杀
Unknown 无法获取 Pod 状态 节点失联

所以你在一个 Pod 里跑 3 个容器，实际上有 4 个容器（1 个 Pause + 3 个业务容器）。这也是为什么 Pod 内的容器能共享网络和存储的原因。

五、Pod 的健康检查

Pod 跑起来不代表它”健康”。K8s 提供了两种探针来判断 Pod 是否正常工作。

5.1 livenessProbe（存活探针）

作用：容器”死了没”？如果探针检查失败，K8s 会重启容器。

适合的场景：程序死锁、无限循环、假死状态。

5.2 readinessProbe（就绪探针）

作用：容器”准备好了没”？如果探针检查失败，Pod 不会从 Service 中接收流量，但容器不会被重启。

适合的场景：应用启动慢、预热中、临时过载。

5.3 三种检查方式

一个常见的坑：initialDelaySeconds 设太小。应用还在启动，探针就开始检查，连续失败后容器被反复重启，陷入 CrashLoopBackOff 循环。经验法则：给足启动时间，宁大勿小。

六、Pod 的资源管理

每个 Pod 可以声明自己需要多少 CPU 和内存。

6.1 requests 和 limits

requests limits
CPU 调度参考，不是硬限制 超出会被限流（throttle）
内存 调度参考 超出会被 OOMKill（容器被杀掉）

生产环境建议：两个都设置，而且 limits ≥ requests。如果只设 requests 不设 limits，一个失控的 Pod 可能吃光节点资源。

6.2 QoS 等级

根据 requests 和 limits 的配置方式，Pod 会被分为三种 QoS 等级：

等级 条件 被驱逐优先级
Guaranteed 所有容器都设了 requests=limits 最低（最不容易被杀）
Burstable 至少一个容器设了 requests 或 limits 中等
BestEffort 啥都没设 最高（最先被杀）

生产环境核心服务建议设为 Guaranteed。

七、Pod 的设计模式

不是所有 Pod 都长得一样。根据容器数量的不同，有几种常见的使用模式。

7.1 单容器 Pod（最常见）

一个 Pod 里就跑一个容器，这是绝大多数场景的做法。Deployment、StatefulSet 管理的都是这种 Pod。

7.2 Sidecar 模式

主容器 + 辅助容器，辅助容器给主容器提供附加功能。

典型场景：日志采集、代理、监控 Agent。

7.3 Ambassador 模式

Ambassador 容器作为”外交官”，代理 Pod 对外的通信。

典型场景：连接数据库的代理容器，主应用不需要知道数据库的地址和认证信息，只需要连 Ambassador 容器的 localhost 即可。

7.4 Init Container（初始化容器）

Init Container 在主容器启动之前运行，全部完成后主容器才启动。

典型场景：

  • 等待依赖服务就绪
  • 初始化配置文件
  • 注册到服务发现

八、静态 Pod

除了通过 API Server 创建 Pod，还有一种叫静态 Pod的方式。

静态 Pod 的 YAML 直接放在节点的指定目录下（如 /etc/kubernetes/manifests），由 kubelet 直接管理，不经过 API Server。

K8s 的控制平面组件（API Server、Scheduler、Controller Manager）本身就是以静态 Pod 的方式运行的。这也是为什么你用 kubectl get pods -n kube-system 能看到它们——kubelet 会自动为静态 Pod 创建一个对应的 Mirror Pod 在 API Server 中。

九、常用操作速查

总结

Pod 是 Kubernetes 的核心抽象，也是你日常打交道最多的资源。本文的关键知识点：

  • Pod 是 K8s 最小调度单元，把紧密耦合的容器打包在一起
  • 每个 Pod 一个 IP，内部容器共享网络和存储
  • Pause 容器是 Pod 的”地基”，负责维持共享命名空间
  • 健康检查（liveness/readiness probe）是保障服务稳定的关键
  • 资源管理（requests/limits）合理设置，避免资源争抢和 OOM
  • 优雅终止很重要，别让请求在关闭时被截断

理解 Pod 是用好 K8s 的基础。后面的 Deployment、Service、Ingress 等概念都是建立在 Pod 之上的。
