Namespace 资源隔离与多环境实践

发表于2026-05-20|更新于2026-05-20|Kubernetes
|字数总计:1.7k|阅读时长:6分钟|阅读量:

Namespace 是什么？

想象你租了一栋办公楼，所有团队挤在一起办公——产品组在调试大屏，测试组在跑压测，开发组在部署新版本。资源抢夺、命名冲突、误操作删库……灾难每天都在发生。

**Namespace 就是 K8s 里的”楼层”**。它把一个物理集群逻辑上切分成多个虚拟集群，每个团队占一层，互不干扰。

但要注意：Namespace 提供的是逻辑隔离，不是物理隔离。不同 Namespace 的 Pod 之间网络默认是互通的（除非你配了 NetworkPolicy）。

为什么需要 Namespace？

三个核心痛点：

问题 没有 Namespace 有 Namespace
资源争抢 一个团队跑满 CPU，其他团队卡死 每个 Namespace 配 ResourceQuota，各用各的
命名冲突 两个团队都想叫 api-server 同名 Service 可以存在于不同 Namespace
权限失控 开发人员可能误删生产资源 RBAC 按 Namespace 限定权限范围

K8s 内置 Namespace

一个新集群默认会带这几个 Namespace：

Namespace 用途
default 没指定 Namespace 时的默认去处
kube-system K8s 核心组件（etcd、CoreDNS、kube-proxy 等）
kube-public 公开可读资源，通常存放集群信息
kube-node-lease 节点心跳租约，用于节点存活检测

实践建议： 永远不要在 default 和 kube-system 里部署业务应用。default 是垃圾桶，谁都能往里扔东西；kube-system 是系统领地，别碰。

资源配额：ResourceQuota

Namespace 如果不设限，一个团队就能把整个集群的资源吃光。ResourceQuota 就是给每层楼装电表——用超了就断电。

关键点：

  • requests vs limits：requests 是保底保障，limits 是天花板。Quota 两者都能限制。
  • 超限行为：创建超过 Quota 的 Pod 会被直接拒绝（状态 Forbidden），不会排队等待。

查看配额使用情况

输出会清晰显示每个资源的 Used 和 Hard，一目了然。

默认资源限制：LimitRange

ResourceQuota 管总量，但管不了单个 Pod 写多大的 requests/limits。LimitRange 补上了这个缺口——给每个”房间”设规矩。

工作流程：

  1. Pod 没写 requests/limits → 自动填充 defaultRequest 和 default
  2. Pod 写了但超过 max → 创建被拒绝
  3. Pod 写了但低于 min → 创建被拒绝

这样就杜绝了两种极端：不写资源限制的”裸奔 Pod”，和一口吃掉 16 核 CPU 的”巨兽 Pod”。

多环境实践方案

方案一：一个集群多个 Namespace

最常见的方式，适合中小团队：

优点： 资源利用率高，管理简单
缺点： 隔离性弱，一个集群挂了全完

方案二：多集群隔离

大厂标配——开发和生产根本不在同一个物理集群：

优点： 物理隔离，安全合规
缺点： 运维成本翻倍

方案三：混合模式（推荐）

开发和预发布共享一个集群（用 Namespace 隔离），生产独占一个集群。兼顾成本和安全。

RBAC 与 Namespace 配合

光分 Namespace 不够，还得控制谁能访问哪个 Namespace：

关键区别：

  • Role + RoleBinding → 限定在某个 Namespace 内
  • ClusterRole + ClusterRoleBinding → 集群全局权限

铁律： 生产环境的 Namespace，开发人员绝对不能有写权限。用 CI/CD 管道来部署，人不能直接操作。

最佳实践清单

  1. 命名规范：<团队>-<环境>，如 payment-dev、payment-staging
  2. 始终配 ResourceQuota：没有 Quota 的 Namespace 等于没有刹车
  3. 始终配 LimitRange：防止裸奔 Pod 和巨兽 Pod
  4. RBAC 严格管控：开发不碰生产，生产只走 CI/CD
  5. 不要在 default 里放任何东西
  6. 不要把不相关的应用塞进同一个 Namespace——Namespace 是按业务/团队切分的，不是按技术层切分
  7. CI/CD 中显式指定 Namespace：部署脚本里写死 -n production，别依赖上下文

坑 3：忘记给 K8s 组件设 ResourceQuota

kube-system 默认没有 Quota，但如果你在里头装了太多插件，照样能把节点资源吃光。给系统组件也加上 LimitRange。

小结

Namespace 是 K8s 多租户的基石。单独使用它只能解决命名冲突，配合 ResourceQuota、LimitRange、RBAC、NetworkPolicy 四件套，才能构建真正的多环境隔离体系。记住：隔离从来不是一个功能，而是一组策略的组合。
