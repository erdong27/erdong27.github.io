Service 服务发现与网络入口

前面三篇聊了架构、Pod、Deployment，今天来聊一个困扰很多人的问题：Pod 之间到底怎么互相通信？外部用户又怎么访问到 Pod 里的应用？

答案就是今天的主角——Service。

一、为什么需要 Service？

先回忆一下 Pod 的一个关键特性：Pod 的 IP 是临时的。

每次 Deployment 更新、Pod 挂掉重建、节点故障迁移，Pod 都会拿到一个新的 IP。更狠的是，滚动更新过程中新旧 Pod 是同时存在的——你根本不知道某个时刻该连哪个 IP。

如果前端直接硬编码后端 Pod 的 IP，只要 Pod 一重建，连接就断了。在微服务架构下，几十个服务互相调用，靠手动维护 IP 表根本不现实。

Service 就是来解决这个问题的。

二、Service 是什么？

用一句话概括：Service 是一组 Pod 的稳定访问入口。

它做三件事：

  1. 给 Pod 提供一个固定的访问地址（不再怕 Pod IP 变化）
  2. 自动发现后端 Pod（通过标签选择器）
  3. 负载均衡（流量自动分发到多个 Pod）

3.2 port 和 targetPort

初学者最容易搞混的两个字段：

  • port：Service 对外暴露的端口（别人连 Service 用的端口）
  • targetPort：Pod 里容器实际监听的端口

就像酒店前台：port 是前台的电话号码，targetPort 是帮你转接到的房间号。

3.3 Service 自己的 IP

每个 Service 创建后也会分配一个 Cluster IP，这个 IP 是固定的，不会随 Pod 的变化而变化。而且 K8s 的 DNS 会自动为 Service 创建一条 DNS 记录：

四、三种 Service 类型

Service 有四种类型（加上 Headless Service），今天重点讲最常用的三种。

4.1 ClusterIP（默认类型）

ClusterIP 是 Service 的默认类型，也是最常用的。

它创建一个集群内部的 IP，只有集群内部的 Pod 才能访问，外部完全访问不到。

适用场景：微服务之间的内部调用。比如订单服务调用库存服务，用 ClusterIP 就够了。

4.2 NodePort

NodePort 在 ClusterIP 的基础上，在每个节点上开放一个端口，让外部可以通过节点的 IP 访问。

访问方式：

几个要点：

  • NodePort 的范围是 30000-32767（可在 kube-apiserver 中修改）
  • 如果不指定 nodePort，K8s 会自动分配一个
  • 每个节点的这个端口都会开放，用哪个节点的 IP 都能访问
  • 生产环境一般不直接用 NodePort（端口不好记、暴露太多端口），而是配合 Ingress 使用

4.3 LoadBalancer

LoadBalancer 在 NodePort 的基础上，自动创建一个外部负载均衡器（通常是云厂商提供的）。

创建后，云厂商会自动创建一个负载均衡器并分配公网 IP：

外部用户直接访问 52.14.xxx.xxx:80 就能打到后端 Pod。

适用场景：

  • 云上环境（AWS、GCP、阿里云等），LB 由云厂商自动创建
  • 本地 Minikube/Kind 环境一般没有 LB 控制器，EXTERNAL-IP 会一直显示 <pending>

五、Service 的流量分发机制

Service 把请求转发到后端 Pod 时，默认使用随机轮询（Round Robin）的方式负载均衡。

5.1 kube-proxy 的工作模式

Service 的底层实现依赖 kube-proxy 组件，它运行在每个节点上，负责维护网络规则。kube-proxy 有三种工作模式：

模式 原理 性能 推荐程度
iptables（默认） 用 iptables 规则转发 规则多时性能下降 ✅ 通用推荐
IPVS 用 IPVS 内核模块转发 高性能，支持多种算法 ✅ 大规模集群推荐
userspace 在用户空间转发 性能最差，已过时 ❌ 不推荐

5.2 SessionAffinity（会话亲和性）

默认情况下，同一个用户的多次请求会被随机分发到不同的 Pod。如果某些场景需要同一个用户的请求固定打到同一个 Pod（比如有本地缓存），可以开启会话亲和：

不过大多数 Web 应用已经通过 JWT、分布式 Session 等方案解决了会话问题，一般不需要开启这个配置。

六、Headless Service

有时候你不需要 Service 做负载均衡，只需要它帮你”找到 Pod”。这时候就用 Headless Service。

Headless Service 不分配 Cluster IP，DNS 查询时会直接返回后端所有 Pod 的 IP：

适用场景：

  • StatefulSet（有状态应用）——需要区分每个 Pod 的身份
  • 自定义负载均衡——应用自己决定怎么分发请求
  • 直接连接特定 Pod——比如数据库主从架构需要分别连主库和从库

总结

Service 是 K8s 网络模型中最核心的抽象，把动态变化的 Pod 包装成一个稳定的访问端点：

  • ClusterIP 是默认类型，适合集群内部微服务通信
  • NodePort 在每个节点开放端口，适合简单的外部访问
  • LoadBalancer 适合云上环境，自动创建外部负载均衡器
  • Headless Service 不做负载均衡，直接暴露 Pod IP，适合有状态应用
  • DNS 发现是最推荐的服务发现方式，简单可靠
  • 排查 Service 问题，第一步永远先看 Endpoint
