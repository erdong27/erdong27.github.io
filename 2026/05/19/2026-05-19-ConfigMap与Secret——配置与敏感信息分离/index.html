ConfigMap 与 Secret——配置与敏感信息分离

你写了一个 Spring Boot 应用，数据库连接串硬编码在代码里。上线要换库？改代码、重新打包、重新部署。测试环境和生产环境配置不同？两套代码分支维护到怀疑人生。

这问题的解法 Kubernetes 早就想好了——把配置从代码里拔出来，交给集群统一管理。ConfigMap 管普通配置，Secret 管敏感信息，各司其职。

为什么要把配置外置？

先看一个反面教材：

三个致命问题：

  1. 改配置必须重新部署——改个端口号都要走一遍 CI/CD
  2. 环境差异靠代码分支管理——dev/prod 不同配置混在代码仓库里
  3. 敏感信息裸奔——密码、Token 明文写在 YAML 里，推到 Git 就是事故

ConfigMap 和 Secret 就是来解决这些问题的。

ConfigMap：普通配置的统一管理中心

本质是什么？

ConfigMap 就是一个键值对存储，用来保存非敏感的配置数据。它最大的价值在于：让配置和镜像解耦。同一个镜像，挂不同的 ConfigMap，就能跑在不同环境。

三种创建方式

方式一：直接用字面量

适合少量配置项，命令行一把梭。

方式二：从文件创建

适合整个配置文件直接丢进去，Spring Boot 的 application.yaml 就这么搞。

方式三：从目录批量创建

目录下每个文件变成一个 key，文件内容就是 value。

3. 挂载为文件（最灵活）

挂载后，ConfigMap 的每个 key 变成 /config 目录下的一个文件。Spring Boot 应用可以直接把 application.yaml 挂到 /config/application.yaml，自动读取，零代码改造。

一个细节：挂载方式更新 ConfigMap 后，Pod 内的文件会自动同步（有约 1 分钟延迟，受 kubelet 同步周期影响）。环境变量方式则不会自动更新，必须重启 Pod 才能生效。

Secret：敏感信息的保险柜

和 ConfigMap 的区别

很多人以为 Secret 就是”加密的 ConfigMap”，这个理解不够准确。核心区别在于：

维度 ConfigMap Secret
数据大小限制 1MiB 1MiB
存储方式 明文 etcd Base64 编码 etcd
访问控制 无特殊限制 可配置 RBAC 独立管控
传输安全 无特殊处理 写入/读取可走加密通道
etcd 加密 默认不加密 可启用静态加密（encryptionConfig）

重点：Secret 默认只是 Base64 编码，不是加密。echo bXlwYXNzd29yZA== | base64 -d 一秒解码。Secret 的安全价值在于：

  1. 访问控制更细——可以通过 RBAC 限制谁能读取
  2. etcd 可加密存储——启用 EncryptionConfiguration 后，etcd 里存的是真正加密的密文
  3. 审计追踪——读取 Secret 会留下审计日志
  4. 与外部密钥管理集成——可以对接 Vault、AWS Secrets Manager 等

生产环境必须知道的坑

1. ConfigMap 更新的延迟问题

修改 ConfigMap 后，挂载方式约 1 分钟同步，环境变量方式需要重启 Pod。如果你需要配置立即生效：

2. Secret 的 Base64 不是加密

永远不要以为 Secret 存在 etcd 里就安全了。生产环境必须启用 etcd 静态加密：

然后 API Server 启动参数加上 --encryption-provider-config。

3. 不可变 ConfigMap 和 Secret

K8s 1.21+ 支持设置 immutable: true：

好处：kubelet 不需要 watch 变更，降低 API Server 负载。适合那些运行后不会再变的配置（如 JVM 参数、时区设置）。想改？删了重建。

4. 大配置项不要用环境变量

环境变量有长度限制（通常 128KB），且进程环境可被 ps e 等命令看到。大配置文件（如 JSON 规则、XML 配置）直接挂载为文件更合理。

5. Secret 不要提交到 Git
