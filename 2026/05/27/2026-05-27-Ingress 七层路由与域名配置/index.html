Ingress 七层路由与域名配置

在前面几天的学习中，我们已经掌握了 Service 的三种类型：ClusterIP、NodePort 和 LoadBalancer。它们工作在 TCP/UDP 四层，能做端口转发，但有一个明显的短板——无法根据 HTTP 请求的域名、路径、Header 做智能路由。

这正是 Ingress 登场的理由。

为什么需要 Ingress？

假设你的集群里跑着三个服务：

  • api.example.com → 后端 API 服务
  • web.example.com → 前端静态服务
  • admin.example.com → 管理后台服务

如果用 NodePort/LoadBalancer，每个服务都要独占一个 IP 或端口，成本和复杂度都很高。而 Ingress 只需一个 LoadBalancer IP，就能根据域名和路径把流量分发到不同的 Service，像 Nginx 反向代理一样工作。

Ingress 是 K8s 的七层（HTTP/HTTPS）流量入口，负责域名路由、路径匹配、TLS 终止等能力。

Ingress 架构：两件套

Ingress 的设计分为两部分：

组件 作用
Ingress 资源 声明式配置（YAML），定义路由规则
Ingress Controller 实际执行路由的组件，负责读取 Ingress 规则并配置底层代理（如 Nginx）

Ingress 资源只是配置，Ingress Controller 才是干活的。 这点和 Deployment 与 kubelet 的关系类似。

常见的 Ingress Controller 实现：

  • NGINX Ingress Controller（最流行，社区活跃）
  • Traefik（配置简单，适合小集群）
  • HAProxy Ingress
  • Envoy-based（如 Contour、Emissary）

核心概念拆解

host（域名）

host 字段指定该规则匹配的域名。不填 host 则为默认后端，匹配所有未命中其他规则的请求。

path / pathType（路径匹配）

pathType 有三个取值：

pathType 含义 示例
Prefix 前缀匹配 /api 匹配 /api/user、/api/v2/
Exact 精确匹配 /health 只匹配 /health
ImplementationSpecific 由 Controller 决定（NGINX 默认同 Prefix） —

注意：/api 的 Prefix 匹配不包含 /api/（末尾有无斜杠有区别），实际使用中建议显式写两条规则或统一路径规范。

backend（后端 Service）

每个 path 都要指定一个后端 Service 及端口，Ingress Controller 会把匹配到的流量转发过去。

路径匹配优先级（NGINX）

当多个路径都能匹配时，NGINX Ingress Controller 按以下规则决定优先级：

  1. 最长前缀优先 — /api/v2 比 /api 优先
  2. Exact 优先于 Prefix
  3. 同长度时按配置文件中的顺序（不保证，勿依赖）

最佳实践：避免模糊的交叉路径，保持路由规则清晰可预测。

常见问题排查

1. Ingress ADDRESS 一直为空

通常是因为 Ingress Controller 没有正常运行，或者 Service 类型不是 LoadBalancer（本地环境需等 NodePort 分配）。

2. 域名访问不通

依次排查：

  1. 域名 DNS 是否解析到 Ingress Controller 的 IP
  2. Ingress 规则的 host 是否与访问域名一致
  3. 后端 Service 是否正常（kubectl port-forward 直连验证）
  4. Ingress Controller 日志是否有报错

3. 路径匹配不符合预期

检查 pathType，确认是否需要末尾斜杠，用 curl -v 观察实际请求路径。

小结

  • Ingress 是 K8s 的七层流量入口，解决 Service 无法做域名/路径路由的问题
  • 架构分两半：Ingress 资源（配置）+ Ingress Controller（执行）
  • 核心配置字段：host（域名）、path/pathType（路径匹配）、backend（目标 Service）
  • 一个 Ingress 支持多域名、多路径，适合统一入口管理
