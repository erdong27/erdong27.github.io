K8s 架构总览与环境搭建

在云原生时代，Kubernetes（简称 K8s）已成为容器编排的事实标准。本文将深入剖析 Kubernetes 的核心架构，并手把手完成本地开发环境的搭建。

一、Kubernetes 架构总览

1.1 整体架构图

Kubernetes 采用主从分布式架构，核心组件可分为控制平面（Control Plane） 和工作节点（Worker Node） 两大部分。

1.2 控制平面组件

kube-apiserver

API Server 是 Kubernetes 的唯一入口，所有组件都通过它进行通信：

  • 提供 RESTful API，供 kubectl、kubelet、其他组件调用
  • 负责请求的认证、授权、准入控制
  • 将集群状态持久化到 etcd

kube-scheduler

Scheduler 负责** Pod 调度**：当用户提交一个新 Pod 时，Scheduler 会：

  1. 过滤（Filtering）：剔除不满足条件的节点（资源不足、标签不匹配等）
  2. 打分（Scoring）：对剩余节点打分，选择最优节点
  3. 绑定（Binding）：将 Pod 绑定到目标节点

调度策略支持标签亲和性、污点容忍、资源请求限制等多种高级特性。

kube-controller-manager

Controller Manager 运行所有控制器进程，核心控制器包括：

控制器 作用
Node Controller 监控节点状态，标记不可用节点
Replication Controller 确保 Pod 副本数符合预期
Deployment Controller 管理 Deployment 的滚动更新
Endpoint Controller 维护 Service 与 Pod 的关联
Garbage Collector 清理已删除资源引用的对象

etcd

etcd 是 Kubernetes 的分布式键值存储：

  • 保存集群所有配置数据和状态
  • 基于 Raft 协议保证强一致性
  • 生产环境建议使用 3 节点及以上集群部署

1.3 工作节点组件

kubelet

kubelet 是运行在每个节点上的 agent：

  • 监听来自 API Server 的指令
  • 管理 Pod 的生命周期（创建、销毁、健康检查）
  • 向 API Server 汇报节点状态

kube-proxy

kube-proxy 实现 Kubernetes Service 的网络代理：

  • 维护节点上的网络规则
  • 支持 iptables 或 IPVS 模式
  • 实现 Service 的负载分发

Container Runtime

容器运行时负责镜像管理和容器执行：

  • Kubernetes 1.24 之后默认使用 containerd
  • 之前版本常用 Docker Engine（通过 dockershim）
  • 其他选项：cri-o、mirantis/cri-dockerd

3.6 对比选型建议

特性 Minikube Kind Docker Desktop K8s

资源占用 较高 低 中等
多节点支持 否 是 有限
Ingress 支持 需插件 需配置 需配置
适合场景 功能测试 CI/CD、快速迭代 Docker 用户

推荐：

  • 入门学习 → Minikube（功能最完整）
  • CI/CD 集成 → Kind（启动快、容器化）
  • 日常开发 → Docker Desktop K8s（已有 Docker 环境）

总结

本文深入剖析了 Kubernetes 的核心架构：

  • 控制平面：API Server（统一入口）、Scheduler（Pod 调度）、Controller Manager（控制器运行）、etcd（状态存储）
  • 工作节点：kubelet（节点代理）、kube-proxy（网络代理）、Container Runtime（容器运行）
  • 本地环境：Minikube 适合功能测试，Kind 适合 CI/CD，根据实际需求选择
