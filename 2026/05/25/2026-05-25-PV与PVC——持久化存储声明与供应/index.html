PV 与 PVC——持久化存储声明与供应

发表于2026-05-25|更新于2026-05-25|Kubernetes
|字数总计:1.6k|阅读时长:5分钟|阅读量:

前言：容器里的数据去哪了？

你有没有遇到过这样的场景：在 Kubernetes 里跑了一个 MySQL 数据库，某天 Pod 因为节点故障被重新调度到另一个节点，结果发现——数据没了！

这不是 Bug，这是容器的”天性”。容器天生就是”用完即弃”的，Pod 里的数据默认只存在于容器内部，Pod 一旦销毁，数据就跟着消失了。

对于无状态应用（如 Nginx），这没问题，随时可以重建。但对于有状态应用（如数据库、消息队列），数据丢失就是灾难。

这就引出了 Kubernetes 持久化存储的核心概念——PV 和 PVC。

一、什么是 PV（PersistentVolume）？

PV 是持久化卷（PersistentVolume）的缩写，是集群级别的资源，代表一块存储。

可以把它理解成”硬盘”——一块真实的、可用的存储空间。它可能来自：

  • 本地磁盘（hostPath）
  • 网络存储（NFS、Ceph、GlusterFS）
  • 云厂商的存储服务（AWS EBS、Azure Disk、阿里云盘）

PV 的核心属性

关键属性解读：

属性 说明
capacity.storage 存储容量，如 10Gi
accessModes 访问模式（见下表）
persistentVolumeReclaimPolicy 回收策略（Retain/Delete/Recycle）
storageClassName 所属存储类，用于 PVC 匹配
volumeMode Filesystem（文件系统）或 Block（块设备）

访问模式（AccessModes）：

模式 缩写 说明
ReadWriteOnce RWO 单节点读写（最常用）
ReadOnlyMany ROX 多节点只读
ReadWriteMany RWX 多节点读写（如 NFS）
ReadWriteOncePod RWOPOD 单 Pod 独占（K8s 1.22+）

二、什么是 PVC（PersistentVolumeClaim）？

PVC 是持久化卷声明（PersistentVolumeClaim）的缩写，是命名空间级别的资源，代表对存储的”需求”。

可以把它理解成”申请单”——用户说”我需要 10Gi 的存储，读写模式是 RWO”，Kubernetes 会根据这个需求去找合适的 PV 进行绑定。

PVC 的核心属性

关键属性解读：

属性 说明
accessModes 需要的访问模式，必须与 PV 匹配
resources.requests.storage 需要的存储大小
storageClassName 指定存储类，用于动态供应
selector 可选，用于精确匹配 PV 的标签

三、PV 与 PVC 的关系

用一句话总结：

PV 是”供应”，PVC 是”需求”，它们通过”绑定”建立联系。

绑定过程

  1. 静态供应：管理员提前创建 PV，用户创建 PVC，Kubernetes 自动匹配并绑定。
  2. 动态供应：用户创建 PVC，Kubernetes 根据 StorageClass 自动创建 PV 并绑定。

绑定条件

PVC 能绑定 PV，必须满足以下条件：

  1. 存储容量：PVC 请求 ≤ PV 容量
  2. 访问模式：PVC 模式 ⊆ PV 模式
  3. 存储类：PVC 的 storageClassName 与 PV 一致（或都为空）

四、PV 的生命周期

PV 有 4 个阶段，完整生命周期如下：

阶段 说明
Available 可用状态，尚未被 PVC 绑定
Bound 已绑定到某个 PVC
Released PVC 已删除，但 PV 还没回收
Failed 自动回收失败

原因：

  • 没有满足条件的 PV 可用
  • StorageClass 配置错误
  • 访问模式不匹配

问题 2：PV 被删除后数据丢失

原因： persistentVolumeReclaimPolicy 设置为 Delete

解决： 重要数据使用 Retain 策略

问题 3：多节点读写需要什么存储？

答案： 使用支持 ReadWriteMany 的存储，如 NFS、CephFS、GlusterFS

最佳实践清单

实践 说明
使用 StorageClass 动态供应更灵活，无需手动创建 PV
生产环境用 Retain 防止误删 PVC 导致数据丢失
合理设置容量 宁可大一点，PVC 不能动态扩容（部分存储支持）
备份数据 PV 不是备份，定期备份到对象存储
使用标签选择器 精确匹配特定 PV

七、静态供应 vs 动态供应

对比项 静态供应 动态供应
PV 创建 管理员手动创建 根据 StorageClass 自动创建
灵活性 低，需提前规划 高，按需创建
适用场景 测试、固定存储 生产环境、云存储
配置复杂度 简单 需配置 StorageClass 和 Provisioner

动态供应会在下一篇 StorageClass 中详细讲解。

总结

PV 是集群中的存储资源，PVC 是对存储的需求声明。它们通过绑定机制，将底层存储与 Pod 解耦，让应用无需关心存储的具体实现。

记住三个核心流程：

  1. 创建 PV（或通过 StorageClass 自动创建）
  2. 创建 PVC 声明需求
  3. Pod 通过 volumeClaim 引用 PVC

这样，你的有状态应用就能拥有真正的持久化存储能力，数据不再随着 Pod 的生命周期而消失。
